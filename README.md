# run-alert

마라톤 대회 일정을 매일 한 번 수집해서, **새로 올라온 대회**와 **접수가 열린 대회**를 알려주는 자동화.

## 왜 만들었나

마라톤 대회는 주최가 제각각이라 정보가 여러 사이트에 흩어져 있다.
문제는 정보를 못 찾는 게 아니라 **접수 오픈을 놓치는 것**이다. 선착순으로 마감되는 대회가 많아서
며칠만 안 들여다봐도 못 나간다. 매일 사이트 서너 개를 도는 대신, 그 일을 자동화했다.

## 무엇을 하나

```
매일 09:00 (GitHub Actions 스케줄)
  │
  ├─ 마라톤GO 국내 대회 일정   ─ Playwright (API 없음)
  ├─ 랭킹마라톤 대회 일정       ─ Playwright (API 없음)
  └─ 러너온 대회 캘린더         ─ Playwright (API 없음)
  │
  ▼  관심 지역·거리로 필터
  ▼  직전 상태와 비교
  │     ├─ 처음 보는 대회        → "새로 올라온 대회"
  │     ├─ 접수예정 → 접수중     → "접수 열림"
  │     └─ 접수중 + 마감 D-3 이내 → "마감 임박"    ← 실제로 놓치는 건 여기
  ▼  Discord 알림 (급한 순서로 배치)
  ▼  data/state.json 갱신 → Express API + 웹 화면이 읽음
```

## 설계에서 신경 쓴 것

### 1. 알림 순서 = 급한 순서

아침에 폰을 보는 3초 안에 "지금 뭘 해야 하는지"가 보여야 한다. 그래서 이 순서로 쌓는다.

1. **접수 마감 임박** — 지금 안 하면 못 나간다
2. **접수 열림** — 오늘 신청할 수 있다
3. **새로 올라온 대회** — 알아두면 되는 정보

실제로 대회를 놓치는 경로는 "몰라서"가 아니라 **"알림은 봤는데 나중에 하지 하다가 까먹어서"** 다.
그래서 접수 오픈 알림과 별개로 마감 D-3 안에 한 번 더 찌른다. 매일 보내면 시끄러우니
같은 대회는 쿨다운 2일을 둔다.

그리고 **셋 다 없는 날에는 아무것도 보내지 않는다.** 매일 "새 소식 없음"이 도착하면
사람이 알림을 무시하기 시작하고, 그러면 정작 중요한 날에도 안 본다.

### 2. "신규 항목"만 봐서는 놓친다

처음엔 이전 수집분에 없던 항목만 골라 알렸다. 그런데 정작 필요한 건
**이미 알고 있던 대회의 접수가 열리는 순간**이다. 그건 새 항목이 아니라 기존 항목의 상태 변화라서
신규 비교로는 절대 안 잡힌다.

그래서 항목별로 직전 상태를 저장하고, `접수예정 → 접수중` 전이를 따로 감지한다
(`src/lib/store.js`의 `reconcile`). 알림에서도 접수 열림을 신규 대회보다 위에 둔다 —
사용자가 당장 움직여야 하는 쪽이기 때문이다.

### 3. 긁어도 되는 곳만 긁는다

수집 대상을 고르기 전에 robots.txt를 확인하고, 결과를 `src/config.js`에 근거로 남겼다.

| 사이트 | 판단 | 근거 |
|---|---|---|
| 마라톤GO | 사용 | `User-agent: * / Allow: /` |
| 랭킹마라톤 | 사용 (공개 페이지만) | `Allow: /`, `Disallow: /api/` → 내부 API는 호출하지 않음 |
| 러너온 | 사용 (`/Marathon`만) | `/Marathon` 명시적 Allow, `/api/`·`/marathon/ics` 는 Disallow |
| 무신사 | **제외** | 기본값이 `User-agent: * / Disallow: /` |
| KREAM | **제외** | robots.txt 확인 불가 → 확인이 안 되면 하지 않는다 |

**API나 RSS가 있으면 화면을 긁지 않는다**는 것도 같은 원칙이다.
러닝화 발매 소스(Nike SNKRS, Hypebeast RSS)는 구현해두고 `enabled: false`로 꺼뒀다 —
이번 범위가 아니라서지, 못 해서가 아니다.

### 4. 상대 서버에 부담을 주지 않는다

마라톤 일정 사이트는 대부분 개인이나 소규모로 운영된다. 대기업 사이트처럼 다뤄선 안 된다.

- 하루 1회만 실행 (`schedule: '0 0 * * *'`)
- 요청 간 3초 딜레이
- 이미지·폰트·미디어 리소스 차단 — 텍스트만 필요하고, 전송량도 줄어든다
- User-Agent에 연락처를 넣어 운영자가 로그를 보고 연락할 수 있게 했다
- 소스당 페이지 수 상한 — 페이지네이션 사고로 수백 번 요청하는 일을 막는다

### 5. 조용히 죽지 않게 한다

자동화의 진짜 실패는 에러가 나는 게 아니라 **아무 일도 안 하면서 성공한 척하는 것**이다.

- **재시도**: 지수 백오프로 3회 (2s → 4s → 8s)
- **실패 알림**: 3회 모두 실패하면 Discord로 알린다
- **셀렉터 드리프트 감지**: 사이트가 개편되면 셀렉터가 안 먹으면서도 예외는 안 난다.
  그래서 **"에러 없이 0건"을 성공이 아니라 이상 신호로 취급**하고 알림을 보낸다.
  실제로 첫 CI 실행에서 이 장치가 마라톤 소스 2곳의 셀렉터 문제를 잡아냈다
- **종료 코드**: 문제가 있으면 CI에 빨간불이 뜨도록 `exitCode = 1`
- **소스별 집계 로그**: 어느 소스가 몇 건 들어와 몇 건 살아남았는지를 남긴다.
  이게 없으면 필터를 깜깜이로 튜닝하게 된다
- **구조화 로그**: JSON 한 줄씩 `data/run.log`, 실패해도 아티팩트로 업로드

### 6. 셀렉터를 눈으로 찍지 않는다

`npm run probe -- <source-id>` 로 대상 페이지의 반복 클래스 조합과 링크 샘플, 스크린샷을 뽑아
셀렉터를 정한다. 사이트가 개편돼도 같은 방법으로 다시 찾을 수 있다.

깊은 클래스 체인 대신 **"상세 링크를 가진 행"을 앵커로 잡고 행 텍스트를 정규식으로 파싱**한다.
마크업이 바뀌어도 텍스트 형식이 유지되면 살아남는다.

### 7. 화면도 테스트로 지킨다

알림이 조용히 망가지면 안 되므로 Express API와 웹 화면에 Playwright E2E 테스트를 붙이고
CI에서 돌린다. Playwright를 남의 사이트 긁는 데만 쓰는 게 아니라 원래 용도로도 쓴다.

## 시작하기

```bash
npm install
npx playwright install chromium

cp .env.example .env      # WEBHOOK_URL 채우기 (없으면 콘솔 출력)

npm run probe -- marathongo   # 셀렉터 확인
npm run collect:dry           # 알림 없이 수집 결과만 출력
npm run collect               # 실제 수집 + 알림
npm run notify:test           # 웹훅 연결만 확인

npm run server                # http://localhost:3000
npm run test:e2e              # E2E 테스트
```

## 구조

```
src/
  config.js            수집 대상, 필터, 예의 규칙, 재시도 정책
  collect.js           엔트리포인트: 수집 → 필터 → 상태 비교 → 알림
  server.js            Express API + 정적 화면
  lib/
    browser.js         Playwright 컨텍스트 (UA, 리소스 차단)
    retry.js           지수 백오프
    store.js           상태 저장, 신규/접수오픈 판정, 마감 임박 선별
    notify.js          Discord 알림 (이벤트 / 실패)
    logger.js          JSON 구조화 로그
  sources/
    marathongo.js      Playwright
    rankingmarathon.js Playwright
    runneron.js        Playwright
    snkrs.js           (보류) Playwright
    hypebeast.js       (보류) RSS
tools/probe.mjs        셀렉터 탐색기
tools/notify-test.mjs  웹훅 연결 확인
tests/e2e/             화면·API E2E
.github/workflows/     collect (스케줄) / e2e (PR)
```

## 알려진 한계

- 각 `sources/*.js`의 셀렉터는 실제 DOM을 보고 확정해야 한다 (`npm run probe`)
- 상태 표기가 사이트마다 달라서(`접수중` / `접수 중` / `신청중`) 정규식으로 흡수하고 있다.
  새 표기가 나오면 `config.js`의 `OPEN_STATUS`에 추가해야 한다
- 대회 연도를 현재 연도로 가정한다. 연말에 다음 해 대회가 섞이면 보정 필요
- 상태를 리포지토리에 커밋해 관리한다. 항목이 수천 건을 넘으면 SQLite로 옮기는 게 맞다
- 윈도우에서는 npm 스크립트가 cmd로 실행돼 `VAR=1 node ...` 문법이 안 먹는다.
  그래서 dry run은 환경변수가 아니라 `--dry` 플래그로 받는다
